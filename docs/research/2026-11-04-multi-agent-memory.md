# Per-user memory, per-agent memory and a hive mind in Oort: scope hierarchy, promotion, privacy and a provable isolation guarantee

Date: 2026-11-04
Status: research and design note for Marcus to accept or reject item by item (see "Open decisions" and "Proposed Linear issues")
Question: how should Oort make (1) per-authenticated-end-user memory and (2) per-agent memory plus a shared "hive" work "100%", both self-hosted and on Oort Cloud?

Inputs read: design doc §5 (memory model, §5.2 Scope), §6 (read and write paths), §8 (the 2026-11-03 implementation note about scope crossing), §9 (cloud, tokens, encryption modes), §10 (phasing), §14 (deletion, audit); the research notes `2026-11-03-temporal-knowledge.md` and `2026-11-03-connectors.md`; and, in `.worktrees/phase-1/packages/`, `core/src/{scope,model,adapters,store-conformance,recall,observe}.ts` and the scope handling in `store-sqlite/src/index.ts`.

## Summary of the recommendation

1. **Isolation is a property of the store boundary, not of a filter the caller builds.** Of the systems whose docs I read, most put the per-user guarantee in caller-built filters or caller-chosen ids (Mem0, LangGraph's OSS store, OpenAI Agents SDK sessions, CrewAI's `private` flag). Oort's design already says this is an anti-goal (A3, "isolation that depends only on a WHERE clause"), but Phase 1 code still has the gap: `get`, `forget`, `recordAccess`, `setTier`, `coldGet` and the cursor methods take no scope, and `upsert` is `ON CONFLICT (id) DO UPDATE` over every column including the scope columns. CON-50 is one symptom of a wider shape problem. Fix the shape: every `MemoryStore` method takes an opaque, verified `Grant`, never a raw filter and never nothing.
2. **Scope becomes a tree of addressable nodes plus a per-request `Grant` that names a set of nodes.** Today `ScopeFilter` is one exact `(org, customer, agent)` plus a project list, so a recall can only ever see one agent's memory. A hive needs "read these N nodes". Proposed levels: `run`, `agent` (agent-private, no end user), `agent-user` (what agent A learned serving user U), `user` (facts about U shared by every agent serving U), `hive` nodes (swarm, team, org; a tree), all under an `org`. `project` stays orthogonal. A discriminated union makes invalid combinations unrepresentable.
3. **Two axes, one rule.** The *subject* axis (the end user) and the *author* axis (the agent) are different. Data flows **upward only through `promote()`**, which creates a new, de-identified memory at the target node with `derivedFrom` edges. A narrower scope may REINFORCE a wider memory or ADD an override at its own level; it may never UPDATE or SUPERSEDE one (this generalises the rule the design already adopted for project vs global in §8).
4. **Read: per-level first-stage recall in parallel, fuse by relevance, tiny specificity prior as tie-break.** Provenance labels are generated by code from structured fields, never from memory text.
5. **Write: narrowest scope by default; promotion is explicit, policy-driven, or consolidation-proposed.** System One may only *deny or route to approval*, never grant. The Collaborative Memory paper itself concedes that LLM-enforced policies can breach, so enforcement stays in code.
6. **User-derived memories never auto-promote.** Default deny; opt-in per org to `approval` or `de-identify-and-k-threshold`. Forgetting a user cascades along `derivedFrom` edges, so hive memory that came from them is removed or re-derived. Keys: user-bearing levels use the customer DEK; subject-less levels use hive DEKs; a key service re-checks the grant before unwrapping.
7. **Tokens:** an org-minted, attenuable capability token (macaroon-style HMAC chain with a closed, typed caveat vocabulary) resolves to a `Grant`. Honest boundary of "100%": Oort cannot authenticate the end user, the company's backend asserts the identity; Oort guarantees that a token minted for user A never returns user B's bytes.
8. **Credibility of "100%"** comes from a non-interference property test (results for a grant are unchanged by anything outside that grant), an adapter conformance suite every store must pass, token fuzzing for monotonic attenuation, canaries in every tenant that must never appear in any output (including logs, errors, caches), mutation testing of the scope predicate, and an external red team before GA.
9. **Before the cloud:** `Grant`-taking store API (completes CON-50), isolation conformance and property tests, the level model with a SQLite migration, multi-level recall with provenance labels, `promote()` plus a local audit log, in-process attenuation and the MCP daemon, the promotion privacy gate, and the forget cascade. The cloud adds token minting, per-level DEKs, the key-service check, approval UI and red-team CI.

## 1. How existing systems model user, agent, session and shared memory

### 1.1 Comparison

| System | Identity axes | Shared / hive concept | Where isolation is enforced (per the docs) |
| --- | --- | --- | --- |
| Mem0 | `user_id`, `agent_id`, `app_id`, `run_id` tags on one record | Filter-built; "Team Task Agent" cookbook shares project memory | Tagging and filter construction by the caller |
| Zep | user (own graph), threads (sessions) | Separate shared "Context Graph" addressed by `graph_id` / `graph_uuid` | API addressing; user id vs graph id |
| Letta | agent; memory blocks | One block attached to many agents | Block attachment; `read_only` is per block, not per agent |
| LangGraph / LangMem | namespace tuples, usually `(user_id, "memories")` | Shared top-level prefix (inference, not stated) | OSS store: none stated; platform: auth handlers must rewrite `namespace` |
| CrewAI | hierarchical scope paths, `source`, `private` flag | Crew memory is shared by default; agents can get a scoped view | `private` flag plus `source` match, caller-supplied |
| AutoGen | per-agent `Memory` protocol | Not in the protocol | The store implementation |
| OpenAI Agents SDK | `session_id` | Multiple agents can share one session | "does not authenticate a user or authorize access"; the app must |
| Google ADK | session, `user:`, `app:`, `temp:` state prefixes | `app:` shared across all users | Service-level |
| AWS AgentCore Memory | `actorId`, `sessionId`, strategy namespaces | Namespace templates | IAM condition keys on `namespace` |
| Supermemory | namespace (hard) plus metadata (soft) | Not covered by the page I read | Scoped API keys that "cannot cross a namespace" |

### 1.2 Per-system notes

**Mem0.**
- One record carries the ids; it is not stored per entity. On the default extraction path "each extracted fact is attributed to whoever stated it, so a record carries `user_id` or `agent_id`, not both". Source: https://docs.mem0.ai/platform/features/entity-scoped-memory
- A filter matches only the fields you specify, and `AND`-ing `user_id` with `agent_id` "only matches records that have both fields set", which the default path never produces; you must `OR`. Same source.
- Mem0's own partitioning playbook warns that "Partial scope leaks data": filtering on `user_id` alone returned memories from another agent's context, and "each search resolves one entity boundary at a time". Source: https://docs.mem0.ai/cookbooks/essentials/entity-partitioning-playbook
- Takeaway: Mem0's model is tag-and-filter. That is exactly the design Oort's anti-goal A3 rejects. The useful ideas to keep are the four identity axes and "attribute the fact to who said it".
- Delete: the entity delete endpoint is asynchronous ("queued for background execution") and the page says nothing about shared memories. Source: https://docs.mem0.ai/api-reference/entities/delete-user
- Graph memory scoping and isolation are not described on the graph page I fetched. UNVERIFIED. Source checked: https://docs.mem0.ai/platform/features/graph-memory

**Zep.**
- A user has threads and one user graph; "the graph doesn't separate data by thread". Deleting a user removes threads, artifacts and the whole user graph in one call, pitched as right-to-be-forgotten. Source: https://help.getzep.com/users
- Sharing across users is a separate Context Graph addressed by `graph_id`; user operations use `user_id`/`thread_id`, shared operations use `graph_id`; group chat messages go in with `graph.add`, not `thread.add_messages`, "because a thread belongs to one user". The v4 page says the graph UUID is server-generated while older pages show custom ids, so the docs disagree. Source: search result summaries for https://help.getzep.com/v4/create-graph and https://help.getzep.com/agent-domain-knowledge
- Takeaway: Zep keeps the person axis (user graph) and the shared axis (context graph) as different resources, with no promotion between them in the docs I saw. That matches the Oort rule "shared memory is a different node, fed deliberately".

**Letta.**
- A block is created once and attached to several agents with `block_ids`; "When one agent updates the block, all others see the change immediately". `read_only=True` stops the memory tools editing it, "applies to the whole block, so you can't make it read-only for some agents and writable for others". Concurrency: `memory_insert` is safe, `memory_replace` fails if the target changed, `memory_rethink` is last-writer-wins and can lose updates; the doc suggests one owner agent for heavy edits. The page covers the legacy v1 API and recommends "shared memory repositories" for new work (details not fetched). Source: https://docs.letta.com/guides/agents/multi-agent-shared-memory
- Takeaway: per-agent permissions on a shared object are exactly what Oort's attenuation caveats must provide ("this agent may read the hive, write only its own scope"), and the hive should be append-mostly with guarded supersede, not last-writer-wins blocks.

**LangGraph and LangMem.**
- Namespaces are tuples such as `(user_id, "memories")`; "Namespaces often include user or org IDs"; cross-namespace search is via content filters. Neither page I read states access control on namespaces. Source: https://docs.langchain.com/oss/python/langgraph/memory
- In the hosted platform, `@auth.on.store` handlers "must rewrite the mutable `namespace` field in `value` to scope data per user" and do not return metadata filters. Source: https://docs.langchain.com/langsmith/auth
- LangMem shows a hierarchical template `("acme_corp", "{user_id}", "code_assistant")` populated at runtime from `configurable`. Source: https://langchain-ai.github.io/langmem/concepts/conceptual_guide/
- Takeaway: a good ergonomic idea (a path whose prefix is the tenant), with enforcement left to a handler the integrator writes.

**CrewAI.**
- One `Memory` class replaces short, long, entity and external memory; scopes are a filesystem-like tree (`/project/alpha`, `/agent/researcher/findings`); a `MemorySlice` is a view over disjoint scopes; "All agents in the crew share the crew's memory unless an agent has its own"; records carry a `source` tag and a `private` flag, visible only when the source matches unless `include_private=True`. Source: https://docs.crewai.com/en/concepts/memory
- Takeaway: `private` plus `include_private` is an API-level convention any caller can flip. In Oort the equivalent must be a caveat in a token that the caller cannot remove.

**AutoGen / AG2.**
- AutoGen's agentchat `Memory` protocol is `add`, `query`, `update_context`, `clear`, `close`; `ListMemory` and a ChromaDB store ship. Nothing in the protocol scopes by user or agent. Source: https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/memory.html (search summary). AG2's own memory and swarm context variables: UNVERIFIED (page 404).

**OpenAI Agents SDK sessions.**
- "A session ID selects conversation history; the session ID does not authenticate a user or authorize access to that history." Agents can share a session; the SDK does not scope by user; the app must enforce access; `EncryptedSession` wraps any session but "does not verify the completeness or order of history". Source: https://openai.github.io/openai-agents-python/sessions/
- Takeaway: this is the honest statement of the problem. A scope id is a selector, not a credential.

**Google ADK.**
- State prefixes: none is session state; `user:` is "shared across all sessions for that user (within the same app_name)"; `app:` is "shared across all users and sessions for that application"; `temp:` is per invocation and never persisted. Source: https://adk.dev/sessions/state/
- Takeaway: a compact precedent for `run`/`user`/`app` levels, and for an ephemeral level that is never persisted.

**AWS Bedrock AgentCore Memory.**
- Namespaces are paths built from templates such as `/strategy/{memoryStrategyId}/actor/{actorId}/`; IAM policies condition `RetrieveMemoryRecords` on `bedrock-agentcore:namespace`; docs recommend a trailing slash so `/actors/Alice/` cannot prefix-collide with `/actors/Alice2`. Source (search summary, not a direct page read): https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory-organization.html . Whether `actorId` works as a condition key on retrieval: UNVERIFIED.
- Takeaway: the prefix-collision point is real for Oort too. The design already hit the same class of bug with `cfg:` project ids (§8); scope keys must be structured tuples, never string-prefix matched.

**Supermemory.**
- A namespace is a "hard isolation boundary (user, tenant, project), carried in the URL"; metadata is "soft dimensions inside a namespace"; scoped API keys cannot cross a namespace. Source: https://supermemory.ai/docs/concepts/how-it-works . Shared spaces: not covered, UNVERIFIED.

**Vector databases as the substrate (relevant to the cloud adapters).**
- Pinecone: "all upserts, queries, and other data read and write operations always target one namespace"; recommends a namespace per customer. https://docs.pinecone.io/guides/index-data/indexing-overview
- Qdrant: a collection per tenant is "rarely the most efficient"; payload partitioning with a `group_id` filter and an `is_tenant` keyword index co-locates a tenant's vectors; "Global requests (without the group_id filter) are slower"; dedicated shards for large tenants. https://qdrant.tech/documentation/guides/multiple-partitions/
- pgvector: "With approximate indexes, filtering is applied after the index is scanned", so a filtered query can return fewer rows; partial indexes for few values, partitioning for many. https://github.com/pgvector/pgvector
- MongoDB Atlas Vector Search: fields to filter on must be declared with `type: "filter"` in the index, "useful ... in a multi-tenant environment"; "Filtered queries are typically slower". https://www.mongodb.com/docs/vector-search/indexes/vector-search-type.md
- Takeaway: Oort's cloud warm tier (Atlas) must declare org and level fields as index filter fields and never post-filter in application code.

### 1.3 What none of the docs gave me

None of the systems above documents all three of: (a) a credential that carries the scope and can only be narrowed, (b) enforcement inside the storage adapter independent of the caller's filter, and (c) a published test strategy for cross-tenant leakage. That is the gap Oort can credibly own. I did not exhaustively survey every project, so read this as "among those I read".

## 3. Isolation engineering and how to prove it

### 3.1 How multi-tenant stores guarantee isolation

- **Postgres RLS.** If RLS is enabled and no policy exists, "a default-deny policy is used". Superusers and `BYPASSRLS` roles "always bypass", table owners bypass unless `FORCE ROW LEVEL SECURITY`. `USING` filters visible rows; `WITH CHECK` validates written rows, and failing `WITH CHECK` raises an error while a non-matching `USING` silently skips (`UPDATE 0`). Policy expressions run before user conditions except `leakproof` functions. "Referential integrity checks, such as unique or primary key constraints and foreign key references, always bypass row security", so a unique violation can reveal that a hidden row exists (a covert channel). Sub-selects in policies read a snapshot and can race under `READ COMMITTED`. https://www.postgresql.org/docs/current/ddl-rowsecurity.html
  - Lessons for Oort: default deny; an explicit write-side check (the equivalent of `WITH CHECK`) that is separate from the read filter; beware uniqueness and existence side channels (relevant to `upsert ON CONFLICT (id)` today); never rely on a check that reads other mutable rows without versioning.
- **Convex.** Identity is read inside each function with `ctx.auth.getUserIdentity()`, derived from JWTs; `tokenIdentifier` combines `subject` and `issuer`. https://docs.convex.dev/auth/functions-auth . There is no platform RLS: it is a library pattern (`convex-helpers`) that wraps `ctx.db`; "The protection applies only to functions built with the wrapped custom functions", and by default access to other tables is allowed unless `defaultPolicy: "deny"`. https://stack.convex.dev/row-level-security
  - Lesson: in the Convex adapter, make the only way to touch the database a `scopedDb(ctx, grant)` wrapper, set default policy to deny, and lint or import-guard raw `ctx.db` outside it.
- **MongoDB Atlas, Qdrant, Pinecone, pgvector.** See section 1.2: pre-filter fields declared in the index, per-tenant payload index or namespace, and the filter-after-scan behaviour of approximate indexes. Oort must choose, per adapter, an index-level partition (so one tenant's query never walks another tenant's graph) over a post-filter.
- **OWASP API1:2023, BOLA.** The failure is attackers changing an object id to reach other users' objects; prevention is an authorization check "on every function that uses client input to access a database record", random unpredictable ids as defence in depth (not a substitute), and tests that block deploys on failure. https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization . This is CON-50's class exactly.

### 3.3 How to prove (or credibly argue) isolation

Techniques, each with the thing it catches. The design is in section 9.

- **Non-interference property** (mine, from the standard information-flow notion; no source fetched): for any grant G, store S and operation sequence, `op(G, S) == op(G, S restricted to nodes visible to G)`. It catches leakage through results, ranks, scores, counts, ordering, and shared-index effects in one statement.
- **Property-based testing** generates the scope graphs, memories, grants and operation sequences. fast-check's `fc.property` and `fc.assert` do this for TypeScript; I confirmed the property API on https://fast-check.dev/docs/core-blocks/properties/ but did not confirm shrinking, seed replay or `fc.commands` model-based testing on that page (UNVERIFIED there; they are documented elsewhere in the library).
- **Conformance suite** every adapter must pass. Oort already has one (`store-conformance.ts`, e.g. `scope-excludes-other-org-customer-agent`); it covers `lexical`, `dense` and `list` only (section 4).
- **Canaries**: a unique high-entropy string per tenant, planted in text, stub, entities, embedding neighbourhood and cold blobs, plus a probe principal in production that queries for it.
- **Fuzzing** scope combinations, ids and tokens.
- **Mutation testing** of the scope predicate (design §4 already schedules a mutation runner for Phase 2).
- **Differential testing** of adapters against each other and against a tiny reference oracle.
- **External review**: a red-team pass and a bug bounty before GA. OWASP also asks for authorization tests that block deploys (same source as BOLA above).

## 4. Where Oort is today (code read at the phase-1 worktree)

Facts from `packages/core/src` and `packages/store-sqlite/src`:

- `Scope = { orgId, customerId, agentId, projectId? }` (`model.ts`). `Memory.scope` is exactly one such address.
- `ScopeFilter = { orgId, customerId, agentId, projectIds: (string|null)[] }`, and `scopeMatches` requires `scope.agentId === filter.agentId` (`adapters.ts`). Consequence: a memory written by agent `claude-code` is invisible to any other agent id, even for the same user. There is no way to express "read my own plus a shared set".
- Scoped methods: `lexical`, `dense`, `list` take a `ScopeFilter`. **Unscoped methods:** `get(id)` ("Unscoped: callers obtain ids from scoped reads" in the interface comment), `forget(id)`, `recordAccess(ids, at)`, `setTier(id, ...)`, `coldGet(id)`, `getCursor(key)`/`setCursor(key, v)`. The guarded writes `expireMany`, `coldPutMany` take memory snapshots and guard on `updatedAt` and `tier`, not on scope.
- `recall.ts` calls `store.get(id)` and `store.coldGet(id)` on ids returned from scoped hits, and `observe.ts` calls `store.get` on ids from hits and from `prior.supersedes`. Those ids come from scoped reads, so today's flows are consistent; the gap is that the store *cannot refuse* a bad id, which is why design §8 says "exact-id lookups in inspect/pin/forget were unscoped" and why CON-50 exists.
- In `store-sqlite/src/index.ts`, `upsert` is `INSERT ... ON CONFLICT (id) DO UPDATE SET <every column except id>`, and the column list includes `org_id`, `customer_id`, `agent_id` (`COLUMNS`). So an `upsert` of an existing id with a different scope reassigns the row. I read the statement and the column list, not every caller; treat it as a probable id-hijack vector to confirm in the first issue.
- The vec0 table stores a `scopeKey` computed with `JSON.stringify([orgId, customerId, agentId])` and a project key, and `dense` passes `scopeKey` and `projectKeys` into the KNN query. Structured keys, not string prefixes: good, keep it (compare the AgentCore trailing-slash advice above).
- `localScope()` hard-codes `{ orgId: 'local', customerId: 'self', agentId: 'claude-code' }`.
- `store-conformance.ts` has `scope-excludes-other-org-customer-agent` and `scope-project-ids-global-and-p1-not-p2`, both using `lexical`, `dense`, `list`. There is no test that `get`, `forget`, `recordAccess`, `setTier`, `coldGet` or cursors respect scope, no write-side test, no multi-scope read, and no property test.
- The temporal note's fields are in `model.ts` (`expiredAt`, `endReason`, `lastConfirmedAt`); reconciliation actions are `NOOP | REINFORCE | ADD | UPDATE | SUPERSEDE` in `adapters.ts` (REFINE and CORRECT from the temporal note were not in the interface when I read it).
- Design §8: a project observation may REINFORCE a global memory but never UPDATE or SUPERSEDE one, and every lookup, chain walk and mutation is checked against the caller's scope filter. This note generalises exactly that rule to hive levels.

## 5. Proposed scope hierarchy

### 5.1 Two axes, not one chain

A single chain `org → team → customer → agent → run` conflates two different questions:

- Who is this memory *about* (the end user, or nobody)? The **subject** axis, which drives privacy, deletion and the per-user guarantee (requirement 1).
- Who *authored and may use* it (one agent, a swarm, a team, the org)? The **audience** axis, which drives the hive (requirement 2).

A memory's address records both. Hive nodes have no subject. Memories with a subject are never visible above the node whose audience was explicitly widened by a gated promotion (and promotion produces a different, subject-free memory).

### 5.2 Levels (Proposal)

```ts
type Address =                          // where a memory lives; one node
  | { level: 'run';        orgId; runId; agentId; customerId?; projectId? }
  | { level: 'agent-user'; orgId; agentId; customerId; projectId? }   // A serving U, private to A
  | { level: 'user';       orgId; customerId; projectId? }            // facts about U, any agent serving U
  | { level: 'agent';      orgId; agentId; projectId? }               // agent's own experience, no user
  | { level: 'hive';       orgId; hiveId; projectId? };               // swarm | team | org; hives form a tree
```

`level` determines which fields are required and which are forbidden; the store validates on every write so illegal combinations cannot be stored (for example `agent-user` without `customerId`, or `hive` with `customerId`).

Which combinations are meaningful:

| Node | Meaning | Example | Visible by default to |
| --- | --- | --- | --- |
| `run` | Working and episodic memory of one run; short TTL; consolidates into `agent-user` or `agent` at the end | "Tried retry with backoff; 429 persisted" | That run's agent |
| `agent-user` | What agent A learned serving user U | "For Alice the billing agent already explained proration" | Agent A when serving U |
| `user` | Facts and preferences about U that every agent serving U should know | "Alice prefers metric units" | Any agent holding a grant for U |
| `agent` | The agent's own experience, not about a person | "The invoice API times out above 500 rows" | Agent A (all users) |
| `hive:swarm` | Shared by a set of agents on a task, TTL-able | Findings from a 50-agent crawl | Swarm members |
| `hive:team` | Shared by a team of agents | Support-team playbook | Team members |
| `hive:org` | Organisation-wide, subject-free knowledge | "Our refund window is 30 days" | Any agent in the org |

Not meaningful, deliberately rejected in v1:
- `(hive, customer)`. A per-user memory shared with a team is a `user` memory whose reading agents are an allow-list in the token, not a new node. Keeping hive nodes subject-free is what makes the privacy rules checkable.
- `run` without `agentId`.
- Hive nodes below `run`. A swarm is a hive node; a run is not.
- Cross-`orgId` anything. Org is the hard boundary (and the key boundary).

**Hive tree.** Hives form a tree: `org ⊃ team ⊃ swarm`. An agent's membership gives a chain of ancestors it may read. "Levels in between" are just more hive nodes; the model needs no new concept for them. A swarm can be created per task and merged upward or dropped when it ends.

**Project axis.** `projectId` stays as the orthogonal optional dimension on every level except that a `run` carries its project implicitly. Semantics stay what the design says: `projectIds: (string|null)[]` where `null` is "global". The existing `private: true` project becomes a promotion ceiling: nothing from a private project may be promoted to a hive node outside that project (design §8 already requires a future cross-project feature to "read it and add a conformance test"; this is that feature).

**Default local mapping (so local mode is a degenerate case, not a separate model).** Local `orgId='local'`, `customerId='self'`. The personal harness writes `user` (facts about Marcus) and `agent-user`. A second harness (Cursor) with a different `agentId` today sees nothing from Claude Code because of the exact `agentId` match; with levels it would see the shared `user` node and a project hive. Local "hive" = the project node.

### 5.3 Grants: a set of nodes, computed from a token

```ts
interface Grant {            // opaque, branded; created only by verifyToken() or localGrant()
  readonly orgId: string;
  readonly read:  NodePattern[];     // which nodes (and projectIds) may be read
  readonly write: NodePattern[];     // which nodes may be written
  readonly promote: { from: Level; to: HiveRef }[];
  readonly principal: { customerId?: string; agentId: string; runId?: string };
  readonly expiresAt: number;
  readonly digest: string;           // stable hash of the normalised grant, for cache keys and audit
}
```

A `NodePattern` is a structured tuple with explicit wildcards (never a string prefix). The `ScopeFilter` of today becomes a degenerate grant (one exact node), so the migration is mechanical.

## 6. Read policy

1. **Resolve the read set.** `effective = requested include ∩ grant.read`. Default `include`: `['self', 'user', 'hive']` where `self = run + agent-user + agent`, `hive = every hive node in the agent's ancestor chain`. A request for a level the grant lacks is an explicit `scope_denied` error in SDK and API, not a silent empty result, so misconfiguration is visible; by-id lookups differ (section 11, uniform `not_found`).
2. **Per-node first-stage recall, in parallel** (design §6.1 step 3, applied per node): BM25 and quantized ANN each over one node's partition, top 50. Each node is its own index partition and its own DEK, so a bug in the fusion code cannot mix candidates, and tiering stays independent per node (a hot org-hive does not displace a user's hot set).
3. **Cold hydration** per node, unchanged.
4. **Fusion: relevance first.** Reciprocal rank fusion of the lexical and dense legs *within* a node as today; then merge nodes by fused relevance. Do **not** weight levels in the first version. Add one small multiplicative **specificity prior** as configuration, default off in Phase 2 and tuned on the eval: `score' = score × (1 + ε_level)`, with ε in `[0, 0.1]`, ordered `run > agent-user > user > agent > swarm > team > org`, so that on near-ties the more specific memory wins. Rationale: the ADK state model and CSS-like cascades both resolve conflicts toward the narrower scope (ADK: https://adk.dev/sessions/state/), and a user's explicit preference should beat an org default.
5. **Cross-level contradictions at assembly time.** If a user-level memory and a hive memory are judged contradictory by the existing Stage C question (cheap, batched), show the narrower one and annotate or drop the wider one. The hive memory is never edited by that conflict (section 7.5).
6. **Budget quotas.** Per-node token budget shares (config, default: hive at most 40% of the injected budget), so a large hive cannot crowd out the user's own memory.
7. **Rerank** across the merged candidates, then top 5 to 10 within budget, as in §6.1.
8. **Access logging.** Reads of a hive memory increment an aggregate activation counter with no per-reader identity, so shared reinforcement works ("the hive learns what is useful") without turning the access log into a record of which user asked what. Increments are batched per node to avoid one hot row (Letta's shared-block guidance about concurrent edits is the cautionary tale: https://docs.letta.com/guides/agents/multi-agent-shared-memory).
9. **Hot injection.** Pinned memories in each readable node are eligible under their node's budget; hive pins (org policy, style) get a small reserved budget.

### 6.1 Injected provenance labels

Every returned memory carries a one-line label built **by code from structured fields**, never from stored text. Brackets and control characters in memory text are escaped so a memory cannot forge a label. Examples:

```
[you, 2d ago]                                   run / agent-user, authored by this agent
[this user, agent:billing, 3d ago]              user or agent-user
[team:support, 3 agents agree, confirmed 5d]    hive, with contributor count and lastConfirmedAt
[org hive, approved by policy:pii-v3, 2026-10-01]   hive promoted through a gate
[hive, unverified, 1 agent, 20m ago]            hive memory from a low-trust contributor
```

Reasons: (a) the model can weigh a user's own statement differently from a hive generalisation; (b) it is the visible half of the A6 "explainable" requirement; (c) trust: other agents' output is untrusted input. The "unverified" marker is the guard against memory poisoning (section 11). `explain(id)` expands the label into the full provenance and decision list.

## 7. Write policy

### 7.1 Default: narrowest scope the token allows

`observe` and `remember` write to the grant's default write node: `agent-user` when a customer is present, `agent` otherwise. A System One question already in the pipeline's spirit chooses among the levels the token permits: "is this fact about the user (preference, profile) or about the agent's work?" Answers map to `user` (shared across the org's agents for U; configurable per org as `userMemory: 'shared-across-agents' | 'per-agent'`, default `shared-across-agents` because requirement 1 is "that user's memory comes back" regardless of which agent asks) versus `agent-user`/`agent`. The model proposes within the permitted set; it cannot widen it.

### 7.2 Promotion

`promote(id, to)` creates a **new** memory at the target node; the source stays where it is. The new memory has its own id, key, validity window and `derivedFrom: [sourceId, ...]`. Reasons: the two can be forgotten independently; different DEKs apply; the hive version is de-identified while the source is not.

Promotion is one step up the tree by default (`agent → swarm → team → org`); skipping a level needs an explicit caveat in the token. Three modes, set per target node by org policy:

| Mode | Who decides | Typical use |
| --- | --- | --- |
| `explicit` | The calling agent or app, if the grant has `promote:to` | Developer-driven "save this for the team" |
| `auto` | A consolidation job proposes; code checks plus System One approve | Subject-free procedural knowledge, within thresholds |
| `approval` | A human approves from a queue (CLI, Observatory §13, cloud console) | Anything touching user-derived content, or org-level |

**Consolidation from individual to collective (Proposal, informed by G-Memory and Generative Agents' reflection).** A periodic job looks for (a) the same claim independently held by at least `k` distinct agents (corroboration), or (b) a cluster of episodic memories with one extracted insight, and creates a *proposal* for the next hive node. The proposal enters the privacy gate below. Nothing reaches a hive without passing the gate or an explicit allow.

### 7.3 The privacy gate (code decides; System One may only restrict)

Order of checks on any promotion:

1. **Hard deny, deterministic code.** Source `level` of `user` or `agent-user`, or any `subjectId` set, is **denied** unless org policy `userDerivedPromotion` is `approval` or `deidentify`. Default: `deny`. Private-project memories are denied beyond their project.
2. **Secret and PII scrub.** The Stage 0 scrubber (A7) runs again, plus pattern PII detectors (emails, phone numbers, account numbers) and an entity-name check against the subject's known names (store hashes, not names, in the check).
3. **System One judgments** via `DecisionController` (typed, calibrated, like `gate` and `reconcile`): `is_generally_useful` and `contains_personal_data`. Thresholds are config. A "no" denies or routes to `approval`; a "yes" never overrides a hard deny. The Collaborative Memory paper's own limitations paragraph is the reason (https://arxiv.org/html/2505.18279).
4. **De-identification by the writer (System Two)** when policy allows user-derived promotion: rewrite into a generalisation with no names, ids, dates tied to a person, and re-run steps 2 and 3 on the output. The paper's shared-tier write policy has the same shape (user-specific details removed). The source text never goes into the hive.
5. **k-threshold for user-derived generalisations (Proposal).** Require the generalisation to be supported by at least `k` distinct customers (default 10) before it can be approved. This is a k-anonymity-style floor, not a privacy proof, and is marked as a design proposal, not sourced.
6. **Audit** every decision, including denials (section 7.6).

### 7.4 Provenance on a hive memory

```ts
interface HiveProvenance {
  derivedFrom: { memoryId: string; node: NodeRef; customerRef?: string }[];  // customerRef = HMAC(orgKey, customerId), never the raw id
  contributors: { agentId: string; at: string; action: 'asserted' | 'confirmed' | 'contradicted'; sourceNode: NodeRef }[];
  gate: { policyVersion: string; mode: 'explicit' | 'auto' | 'approval'; approvedBy?: string; decisions: Decision[] };
  support: { agents: number; customers?: number };   // counts only, no ids
}
```

`derivedFrom` is the edge the deletion cascade follows. `customerRef` is a keyed hash so a cascade can find "everything derived from Alice" without storing Alice's id in the hive; destroying the HMAC mapping at forget time makes the audit trail unlinkable afterwards. `contributors` supports the "which agents taught the hive this" explanation, and `support.agents` drives the `3 agents agree` label.

### 7.5 Conflicts between agents' facts

Reuse the validity model from design §5.4 and the temporal note (valid time, transaction time `expiredAt`, `endReason`, `lastConfirmedAt`). Rules for hive nodes:

- **Same node, contradictory claims.** Reconciliation runs against hive candidates exactly like Stage C. For SUPERSEDE, order by **observation time (`validFrom`)**, not arrival time: the temporal note's out-of-order guard applies even more here because 50 agents report late. A misordered arrival closes the new memory, not the old one.
- **Provenance survives.** The superseded memory stays as history with `endReason: 'superseded'` and keeps its contributors; the new one lists `supersedes`. Nothing a contributor said is erased by someone else's claim.
- **CORRECT vs SUPERSEDE.** If the later claim says the earlier was wrong (not that the world changed), use the temporal note's CORRECT (`endReason: 'corrected'`).
- **Trust gate on destructive change.** A contradiction from a contributor below the hive's `supersedeTrust` threshold does not supersede; it becomes a `needs-review` proposal, and both claims are served with the label `contested`. Default trust per agent is a field on the token, not self-asserted.
- **Concurrency.** Hive writes go through a per-node serialised writer (a queue or the guarded writes the store already has: `GuardedWriteResult` skips if `updatedAt` or `tier` changed). Hive stays append-mostly; edits are guarded supersedes, not "last writer wins" (contrast Letta's `memory_rethink`).
- **Across levels, no supersede.** A user or agent observation may REINFORCE a wider memory (an anonymous counter bump, no contributor row, so a user's confirmation is not recorded in the hive) or ADD an override at its own level. It may never UPDATE or SUPERSEDE a memory in a wider node. This is the rule design §8 adopted for project vs global; it generalises to every level. Conformance test: observing in `agent-user` with a contradicting fact leaves the hive row byte-identical.

### 7.6 Audit log

Append-only, per org, never containing memory text (design §14.3):

`{ ts, jti, principal: { orgId, customerRef?, agentId, runId? }, op, nodes[], memoryIds[], result: allow|deny|pending, reason, policyVersion, approver? }`

Denials are logged, because probing shows up as repeated denies. Entries survive account deletion (identifiers and timestamps only). Admin and approval actions carry the human's identity. Local mode writes the same record shape to a local table so the cloud format is not a rewrite.

## 8. Privacy, deletion, keys

### 8.1 Rules

- An end user's personal facts are never promoted to an org-wide hive without policy (7.3, step 1). The default org policy is deny.
- Hive nodes are subject-free by construction (the `hive` address has no `customerId`).
- Operators never see memory text (design §9); the console shows metadata and counts, and audit entries show ids only.

### 8.2 Forget cascades

`forgetCustomer(U)` (an org-admin capability; also reachable by the end user's own token for `forget` on their own nodes):

1. Mark U's nodes (`user`, `agent-user`, `run` with `customerId=U`) as tombstoned in one transaction; reads stop immediately.
2. Follow `derivedFrom` edges from U's memory ids (via `customerRef` index) to hive memories. For each:
   - only U contributed: delete it;
   - other contributors exist: remove U's contribution and mark `needs-rederive`; the writer regenerates without U's source or the memory is deleted if support falls under the k-threshold;
   - `customerRef` rows are deleted, which unlinks the audit trail.
3. Promotions in flight (pending proposals sourced from U) are cancelled; a promote racing a forget loses (the tombstone check is part of the guarded write).
4. Destroy U's DEK (crypto-shred, design §14.3). Physical purge and backups follow the §14.3 schedule.
5. Return a receipt listing counts per node and the purge deadline, as §14.3 requires.

This is the piece the Collaborative Memory paper leaves open (revocation effect on shared fragments). Mem0's and Zep's docs describe entity deletion but say nothing about derived shared records (Mem0 page explicit that it doesn't say; Zep's user delete covers the user's own graph and threads: sources in section 1.2).

### 8.3 Keys per level (ties to §9 managed vs zero-knowledge)

| Node | Key | Notes |
| --- | --- | --- |
| `user`, `agent-user`, `run` with customer | customer DEK | Forget U = shred this key; one key covers every user-bearing node |
| `agent` | agent DEK | No end user involved |
| `hive` (swarm, team, org) | one DEK per hive node | Hive memories are de-identified, so shredding a customer DEK does not and need not shred them; the cascade in 8.2 removes derived rows |
| Blind-index HMAC keys | one per node | In `encrypted` mode the lexical leg is per-node, which matches per-node recall in section 6 |

- **Managed mode:** a key service holds KEK-wrapped DEKs. The `unwrap(keyId, grant)` call **re-checks that the grant covers the key's node**, so a store-layer bug alone cannot decrypt another tenant's data. This is defence in depth; the store check remains primary.
- **Zero-knowledge mode:** the client holds the customer DEK and the hive DEKs it is entitled to. Distributing a hive key to 50 agents is a key-capability problem: the token carries wrapped key grants only for the nodes it names, and attenuation removes entries. Inversion risk stays as documented in design §9: embeddings can be inverted; Morris et al. recover about 92% of 32-token inputs exactly from dense embeddings (https://arxiv.org/abs/2310.06816). So hive embeddings in zero-knowledge mode carry the same caveat, and de-identification before promotion matters more there.

## 9. API shape

### 9.1 Tokens and attenuation

Who authenticates whom: Oort cannot authenticate the company's end user. The company's backend (which already authenticated the user) mints a **context token** for each request or session. Oort's guarantee is conditional: for a token minted for `(org, customerId=A, agentId=X)`, every returned byte originates from nodes that token grants. If the company mints a token for the wrong user, Oort will faithfully serve the wrong user; that is outside the boundary and must be stated in the docs and the DPA.

**Recommendation (Proposal): a macaroon-style capability token with a closed, typed caveat vocabulary.**
- Root minted by Oort (or by a company backend holding an org signing key) with an HMAC chain per the macaroons construction (see 3.2).
- Closed caveats, so verification is set intersection and is property-testable: `org`, `customer`, `agent`, `run`, `read ⊆ levels`, `write ⊆ levels`, `promote ⊆ (from,to)`, `hives ⊆`, `projects ⊆`, `exp`, `aud`.
- Attenuation is monotonic: adding a caveat can only shrink the grant. A 50-agent orchestrator receives a broad token and hands each worker an attenuated one: "read hive:team and my own scope; write only `agent:W7` and `run:R`; no promote".
- Cloud edge: also accept a JWT (EdDSA) with RFC 8693 delegation semantics (`sub` = end user, `act.sub` = agent) and convert it to the same `Grant`, so companies with an IdP can use it directly and the MCP connector's OAuth flow works.
- **Alternative:** PASETO `v4.public` for the root plus attenuation by server-side exchange (RFC 8693) instead of offline caveats. Simpler to reason about, no offline attenuation. Decision for Marcus (section 14). Risk of the macaroon path: Oort ships a small HMAC-chain implementation (about 200 lines); mitigate with test vectors and fuzzing (section 10). JS macaroon library quality: UNVERIFIED, so do not depend on one without review.
- **Local mode:** no tokens. A `localGrant()` is built in-process by trusted config; the same `attenuate(grant, caveat)` function is used so MCP clients can only narrow. Serialisation lands with the cloud.
- Lifetime and replay: short `exp` (minutes), `aud` bound to the Oort resource, `jti` recorded for mint-privileged operations, optional DPoP-style sender binding for long-lived agent runtimes (RFC 9449 above).

### 9.2 SDK (`@oortmem/sdk`, extends design §7)

```ts
const mem = oortCloud({ token });          // token minted by the company backend; scope is NOT a parameter

await mem.recall({
  query: 'why did the export fail?',
  include: ['self', 'user', 'hive'],       // subset of what the grant allows; default = all granted
  projectIds: [null, 'checkout'],
  asOf: undefined,
});
// -> { hits: [{ id, text, label, explain: { node, tier, stage, activation, provenance } }] }

await mem.remember({ text, type: 'preference', visibility: 'user' });  // visibility <= grant.write; default 'agent-user'
await mem.observe(observation);                                          // as today, writes to the grant's default node

await mem.promote(id, 'team');           // -> { status: 'promoted', hiveId } | { status: 'pending', proposalId } | { status: 'denied', reason }
await mem.proposals.list({ node: 'team' });        // approval queue
await mem.proposals.approve(proposalId);           // needs an approver capability
await mem.forget({ id });                          // by id, scoped
await mem.forgetCustomer(customerId);              // admin capability; runs the cascade
await mem.explain(id);                             // full provenance and decisions
```

Self-hosted `createMemory({ store, embed, rerank, decide, write, grant })` takes the same shape; `grant` comes from `localGrant()` or `verifyToken()`.

### 9.3 Mapping to MCP tools (connectors note §1, §5)

- Tools stay `recall`, `remember`, `observe`, `pin`, `forget`, `explain`, `inspect` (design §7 and the connectors note) plus `promote`.
- **Scope is never a tool argument.** It comes from the OAuth access token, whose audience is validated and which is never passed through to other services (MCP authorization, per the connectors note citing https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/index.md). The model-visible arguments are `include` and `visibility`, enums limited to the grant; the model can narrow, never widen.
- For 50 agents behind a connector, each agent connects with its own delegated token (RFC 8693: end user as subject, agent as actor).
- `tools/list` is per grant: `promote` is absent unless the grant has it. The 2026-07-28 spec adds `ttlMs` and `cacheScope` on list results (changelog in the connectors note); set `cacheScope` to private per principal so one user's tool list is never served to another.
- Annotations: `recall`, `explain`, `inspect` read-only; `remember`, `observe`, `promote` write but not destructive; `forget` destructive. `promote` needs a human-confirm path in chat hosts (elicitation or the host's confirmation), which also serves the `approval` mode.
- Directory policy risk already noted in the connectors note (persistent cross-session behaviour change) applies and is more acute for a hive; keep the hive off by default for directory-listed connectors.

## 10. The isolation guarantee: where it lives and how it is proven

### 10.1 Enforcement location (layers, outermost to innermost)

1. **Edge:** verify the token (signature, `exp`, `aud`, `jti`, caveat monotonicity) and build a `Grant`. Application and SDK code never construct filters.
2. **Store adapter boundary (primary):** every `MemoryStore` method takes a `Grant`. Adapters compile it into the query *inside the database*: SQL `WHERE`, Atlas `$vectorSearch.filter` on declared filter fields, a Convex `scopedDb` wrapper. Nothing post-filters in application code.
3. **Index partitioning:** one ANN partition per node (sqlite-vec `scopeKey` today; Atlas filter fields plus per-org collection for dedicated tiers; Qdrant-style `is_tenant`; pgvector partitions), so one tenant's query does not traverse another tenant's graph.
4. **Crypto (managed, defence in depth):** `unwrap(keyId, grant)` re-checks the node, so a logic bug yields ciphertext. In zero-knowledge mode the missing key is the boundary.
5. **Writes:** an explicit write-side check (the `WITH CHECK` analogue): the memory's address must be inside `grant.write`, and `upsert` of an existing id must keep its address (fixes the `ON CONFLICT` reassign).

Adapter changes (supersedes CON-50 and widens it): `get(id, grant)`, `forget(id, grant)`, `recordAccess(ids, grant, at)`, `setTier(id, tier, grant, snapshot?)`, `coldGet(id, grant)`, `getCursor/setCursor(key, grant)` (namespaced per grant), and the guarded writes accept only snapshots whose address is inside `grant.write`. Unknown id and not-permitted id return the identical result (`null`) with indistinguishable timing as far as practical.

The `Grant` is branded and constructible only in a small `auth` module; TypeScript will not let application code pass a raw filter. In JavaScript a brand can be forged in-process, so the cloud path re-verifies from the token server-side, and local mode makes no adversarial claim against code running in the same process (see 10.4).

### 10.2 Test strategy

- **Isolation conformance suite v2** (extends `store-conformance.ts`): parameterised over every adapter; for **every public method × every ordered pair of distinct principals**, assert no read, write, existence signal, access-log change or cold-blob read crosses. Required for the sqlite, convex and atlas adapters to ship.
- **Non-interference property** (fast-check): generate a random scope graph (orgs, customers, agents, hive tree), random memories with distinct canaries and near-duplicate embeddings across tenants, random grants (including random attenuation chains), and random operation sequences (recall, list, get, upsert, promote, forget, tier moves). Property: `result(grant, S) == result(grant, S|visible(grant))`, covering ids, order, scores and counts. Counterexamples shrink to a minimal leak. Run a large seed budget nightly, a small one per commit, and log failing seeds for replay.
- **Reference oracle:** a naive in-memory store of about 50 lines that implements the visibility rules literally; adapters are differential-tested against it.
- **Token fuzzing:** drop a caveat, reorder caveats, append a widening caveat, truncate, flip a bit in the HMAC, swap org keys, expire, change `aud`. Properties: `visible(attenuate(g, c)) ⊆ visible(g)` and any tampered token fails closed.
- **Scope fuzzing:** empty strings, `null` vs `undefined` vs `''` for `projectId`, unicode look-alikes, separators, SQL `LIKE` wildcards, ids that look like other ids, `__proto__`, very long values, the `cfg:` collision class (§8). Level/field combinations that are illegal must be rejected at write.
- **Canaries:** every test tenant gets a canary memory (a unique high-entropy string in text, stub, entities, an embedding adjacent to other tenants' queries, and a cold blob). After each test the harness scans **every output channel** (results, errors, logs, audit entries, metrics labels, traces, MCP responses, cache keys and values) for foreign canaries. In staging and production, a synthetic probe principal runs recall and by-id lookups designed to hit another tenant's canary and pages on any hit.
- **Mutation testing** (design §4, Phase 2 runner): the scope predicate and grant module must kill all mutants (target 100% for that module; report the number rather than promise it).
- **Static guards:** an import-graph rule (design §4) bans raw database handles outside the adapter; a semgrep or lint rule bans `ctx.db` outside `scopedDb` in the Convex adapter, because the platform's RLS pattern is opt-in and default-allow (section 3.1).
- **Differential adapter tests** with identical op sequences, comparing visible sets across sqlite, convex and atlas.
- **Cross-tenant red-team job** in CI against a deployed preview: two orgs, 50 agents, adversarial scripts including token replay, id enumeration and prompt-injection promotes.
- **A 50-agent simulation** as the integration test for the hive: private memories diverge, promotions land, a user is forgotten, and the property and canaries are re-checked after every step.
- **External pen test and bug bounty** before GA.

### 10.3 What "100%" can honestly mean

Say this in docs: *for a valid token, every byte returned was stored in a node the token grants, checked at the store boundary and re-checked at key unwrap; this is verified by a non-interference property on every commit, by per-tenant canaries in production, and by an external review.* It is not a mathematical proof of the implementation. Known residual risks, to disclose: the company minting a wrong token; KMS or operator compromise in managed mode; embedding inversion in zero-knowledge mode (Morris et al., above); timing and size side channels; and any LLM judgment (never an enforcement point by design).

### 10.4 Local mode

SQLite is a file readable by the same OS user, and the design already hardens the store directory (`private-fs`, 0600 files, trust bindings for project ids). The local guarantee is **correctness between scopes in one process and store** (the multi-harness, multi-project case), not isolation from a hostile process running as the same user. Say so.

## 11. Threat model

| Threat | How it shows up in Oort | Mitigation |
| --- | --- | --- |
| **Confused deputy** | A service with broad authority (MCP connector, orchestrator, consolidation job, the admin API) acts on a lesser principal's behalf. A prompt-injected agent with hive-write promotes a user's private fact or reads other users via a shared service credential. (Classic confused-deputy formulation, Hardy 1988: UNVERIFIED, not fetched.) | No ambient authority: every store call carries the *end user's* grant, never a service credential; connectors have no store access except through the caller's grant; `promote` is its own caveat and is off by default; scope is never a model-visible argument; consolidation runs with a system grant that can only create *proposals* for user-derived content; RFC 8693 delegation makes the actor explicit in audit. |
| **Token replay and theft** | A leaked bearer token works anywhere | Short `exp`, `aud` binding, `jti` tracking on mint and promote, optional DPoP-style sender constraint for runtimes, scrub token-shaped strings in logs (the A7 scrubber already matches JWT shapes), revocation list keyed by `jti`. |
| **Cross-tenant id guessing via `get(id)`** | The BOLA pattern; `get` is unscoped today | `Grant` on every by-id method, random 128-bit ids as defence in depth (OWASP recommends random ids but as an addition to authorization checks), uniform `not_found`, conformance test on every method. |
| **Id hijack by upsert** | `ON CONFLICT (id) DO UPDATE` rewrites the scope columns of an existing row | Write-side check; address immutable after creation; conformance test. |
| **ANN and embedding leakage in a shared index** | Filtered ANN on a shared graph: post-filtering returns fewer results (pgvector README), scores and counts differ with other tenants' data, search cost reveals neighbours; in zero-knowledge mode embeddings can be inverted | Per-node partitions; index-level pre-filter (Atlas filter fields, Qdrant `is_tenant`); never post-filter in code; never return raw scores across tenants; dedicated index per org on Enterprise; non-interference property includes scores and counts. |
| **Cache keys** | Result cache, rerank cache, MCP `tools/list` cache, CDN and Workers cache, Convex reactive subscriptions serve one principal's entry to another | Cache key = `H(grant.digest ‖ query ‖ policyVersion ‖ nodeVersion)`; `cacheScope: private`; `Cache-Control: no-store` on memory responses; negative results are cached per grant too; embedding cache keyed on text only is acceptable only because it holds no scope-dependent data. How Convex reactive queries key subscriptions by identity: UNVERIFIED. |
| **Memory poisoning through the hive** | A compromised or confused agent writes an instruction-like memory that 49 agents then read as trusted | Per-agent trust on the token; `unverified` label; promotions from untrusted agents go to `approval`; hive memories are typed (instructions are `procedural` and flagged); labels are code-generated; the scrubber runs on the read path too (design §6.2). |
| **Cross-level inference** | A hive fact reveals one user | De-identification, the k-threshold, user-derived default deny, human approval, audit. |
| **Deletion races** | A promote lands after the forget | Tombstones in the guarded write; cascade is idempotent and re-runnable; receipt lists counts. |
| **Revocation staleness** | An agent keeps a derived copy after losing hive access | Reads are checked at read time against the current grant, not at write time; memories already injected into a context window cannot be recalled by Oort; document it. (The Collaborative Memory paper evaluates dynamic grants and revocations on accuracy, but its body does not describe effects on already-shared fragments.) |
| **Operator access** | Staff read memory text | Design §9: metadata-only console, audit of privileged actions, zero-knowledge mode. |
| **Cursor and key collisions** | `getCursor(key)` is global | Namespaced per grant. |

## 12. Phasing against design §10

**Can land before the cloud (Phase 1 hardening and Phase 2, all local):**
- A `Grant` type and `Grant`-taking `MemoryStore` (completes CON-50 and the rest of the unscoped methods; fixes the upsert reassign).
- Isolation conformance v2, the non-interference property test, the reference oracle, canaries and the scope fuzzer. All of this runs against SQLite today.
- The level model (`Address` union, `runId`, hive nodes) with a SQLite migration, and multi-node read sets.
- Multi-level `recall` with `include`, per-node partitions, specificity prior (default off), quotas and code-generated provenance labels.
- `remember({ visibility })`, explicit `promote`, `derivedFrom` provenance, and the local audit log.
- In-process attenuation and a daemon/MCP that only narrows (with CON-18).
- The promotion privacy gate with Jev judgments, approval queue in the CLI, hive conflict reconciliation, and the forget cascade (without crypto-shred).
- A 50-agent local simulation and eval.

**Phase 3 (cloud):**
- Token minting API, org signing keys, JWT/RFC 8693 bridge, `jti` revocation.
- Per-level DEK hierarchy and the key-service grant re-check; BYOK; zero-knowledge key distribution.
- Atlas adapter with filter-field partitioning, Convex `scopedDb` adapter, and the same conformance suites.
- Approval UI in the console and Observatory (§13); org policy editor; deletion receipts and the purge schedule (§14.3).
- Red-team CI, production canary probe, external pen test.

**Phase 4:** per-org dedicated indexes, hive-level analytics, swarm lifecycle tooling.

## 14. Open decisions for Marcus

1. **Default write level for facts about a user:** `user` (shared across the org's agents) or `agent-user` (private to the agent)? I proposed `user` by default, per-org configurable.
2. **User-derived promotion:** allow at all? I proposed default `deny`, opt-in to `approval` or `de-identify + k-threshold`.
3. **Token format:** macaroon-style attenuation (offline, closed caveats) or PASETO root plus RFC 8693 exchange?
4. **Hive in directory-listed connectors:** off by default, as above?
5. **Hive reinforcement privacy:** is an anonymous aggregate counter on reads enough, or should hive reads leave no trace at all?

## Proposed Linear issues

Not created. Each is an independently grabbable vertical slice, ordered by dependency. Numbers in brackets are my proposed order, not Linear ids.

### 1. Grant-gated MemoryStore: scope every by-id and mutating method (completes CON-50)

**What to build.** Introduce an opaque, branded `Grant` type (built only by `localGrant()` for now) and change every `MemoryStore` method to take one: `get`, `forget`, `recordAccess`, `setTier`, `coldGet`, `getCursor`/`setCursor`, and the guarded writes. Add a write-side check so `upsert` rejects an address outside `grant.write` and an existing id whose address would change. Migrate `recall.ts`, `observe.ts`, the CLI and the SQLite store. Unknown id and not-permitted id both return `null`. Today's `ScopeFilter` becomes a one-node grant, so behaviour is unchanged for existing callers.

**Acceptance criteria**
- [ ] No `MemoryStore` method can be called without a `Grant`; the type system rejects a raw `ScopeFilter`.
- [ ] `get`, `forget`, `recordAccess`, `setTier`, `coldGet`, cursors and guarded writes return nothing, change nothing and signal nothing for ids outside the grant (uniform `null`/skipped).
- [ ] `upsert` of an existing id with a different address is rejected and leaves the row unchanged (test reproduces the current `ON CONFLICT` reassign first).
- [ ] The existing conformance tests pass unchanged apart from the call signature; `pnpm verify` is green.

**Blockers.** CON-50 ("Scoped get(id, filter)"): this issue absorbs it; if CON-50 lands first with a `ScopeFilter` argument, this issue migrates that argument to `Grant`. Design §5.2 and §8 (implementation note).

### 2. Isolation conformance v2, non-interference property test and canaries

**What to build.** Extend `store-conformance.ts` into a mandatory isolation suite: every public method times every ordered principal pair, including write-side and cold-blob paths. Add a fast-check non-interference test over generated scope graphs, grants and operation sequences, with a ~50-line reference oracle store. Plant a canary per tenant (text, stub, entities, adjacent embeddings, cold blob) and scan every output channel in the harness. Add a scope fuzzer for id, null/undefined/empty and separator edge cases. Run on the SQLite store.

**Acceptance criteria**
- [ ] Suite exported as `@oortmem/core/store-conformance` and required by SQLite store tests.
- [ ] Non-interference property passes for results, order, scores and counts, with the failing seed printed for replay; per-commit budget plus a larger nightly budget.
- [ ] A deliberately broken store (post-filtering in app code, or an unscoped `get`) is caught by the suite (mutation check of the test itself).
- [ ] Canary scan covers results, errors, logs and audit output; a planted leak fails the test.

**Blockers.** Issue 1 (needs the `Grant` API). Design §4 (mutation and import-graph guards arrive in Phase 2) for the follow-up mutation run.

### 3. Scope level model: `Address` union, `runId`, hive nodes and a SQLite migration

**What to build.** Replace the flat `Scope` with the discriminated `Address` union (`run`, `agent-user`, `user`, `agent`, `hive`) plus an optional `projectId`, validate illegal combinations at write, and give `Grant` a node set (`read`, `write`) with structured `NodePattern`s. Add a SQLite schema version bump and migration that maps existing rows, keeping the `scopeKey` partition for vec0. Hive nodes form a tree (`org ⊃ team ⊃ swarm`) with membership in the grant.

**Acceptance criteria**
- [ ] Illegal level/field combinations cannot be stored (type-level and a database CHECK).
- [ ] A grant with several nodes returns the union of those nodes only; the non-interference suite from issue 2 passes with multi-node grants.
- [ ] Migration is reversible in tests on a copy of a real Phase 1 store and preserves ids, tiers and cold blobs.
- [ ] Two agent ids for the same user can share a `user` node and not each other's `agent-user` nodes (test).
- [ ] `projectIds` semantics unchanged; `private: true` is honoured as a promotion ceiling in the model (enforced in issue 5).

**Blockers.** Issue 1. Design §5.2 (Scope), §8 (project-aware store).

### 4. Multi-level `recall`: `include`, per-node recall, fusion with specificity prior, provenance labels

**What to build.** Run first-stage recall per readable node in parallel, merge by fused relevance with an optional small per-level prior (default off) and per-node token quotas, then rerank. Return code-generated provenance labels (escaped, never derived from memory text) and an `explain` block with node, tier, stage and age. Expose `include: ['self','user','hive']` in the SDK and the CLI. Add the cross-level contradiction display rule (narrower wins at assembly).

**Acceptance criteria**
- [ ] `include` is intersected with the grant; requesting a non-granted level returns a typed `scope_denied`.
- [ ] A memory whose text contains `[org hive, approved]` cannot change its own label (test).
- [ ] With the prior off, results equal single-node recall ordering for single-node grants (regression test against current behaviour).
- [ ] Per-node quotas honoured; the hive cannot exceed its share of the budget.
- [ ] A 50-agent local simulation shows hive recall surfaces a promoted fact to agents that never saw it, with the label naming contributor count.

**Blockers.** Issue 3. Design §6.1 (read path), §6.2 Stage 0 (scrubber on read path).

### 5. `remember({ visibility })`, explicit `promote`, `derivedFrom` provenance and the local audit log

**What to build.** Add `visibility` to `remember`/`observe` (bounded by `grant.write`), a `promote(id, to)` that creates a new subject-free memory at the next hive node with `derivedFrom` and `contributors`, one-step-up semantics, and the `private: true` project ceiling. Add the append-only audit table (no memory text, denials included) with the cloud record shape. Hard rule: source memories with a subject are denied unless org policy allows (default deny).

**Acceptance criteria**
- [ ] Promoting a `user` or `agent-user` memory is denied by default and the denial is audited.
- [ ] Promoting an `agent` memory to a hive creates a new id with `derivedFrom`, leaves the source unchanged, and writes an audit entry.
- [ ] Skipping a hive level without the explicit caveat is denied.
- [ ] A memory from a `private: true` project cannot be promoted outside its project (conformance test, as design §8 requires).
- [ ] Audit entries contain ids, node refs and decisions, never memory text (test scans a leak).

**Blockers.** Issue 3. Design §5.2, §8 (private project rule), §14.3 (audit).

### 6. Attenuable capability tokens and a narrow-only local daemon/MCP

**What to build.** A small `auth` module: a macaroon-style HMAC-chain token with a closed caveat vocabulary (`org`, `customer`, `agent`, `run`, `read`, `write`, `promote`, `projects`, `exp`, `aud`), `verifyToken` to `Grant`, and `attenuate(grant | token, caveat)`. Use it in the local daemon and MCP server so scope is never a tool argument and tool lists are per grant. Include the JWT/RFC 8693 conversion stub as an interface only. Decide the token format with Marcus first (open decision 3).

**Acceptance criteria**
- [ ] Attenuation is monotonic: property test `visible(attenuate(g,c)) ⊆ visible(g)` over random chains.
- [ ] Token fuzz (dropped, reordered, appended, truncated, bit-flipped, wrong key, expired, wrong `aud`) always fails closed.
- [ ] MCP `recall`/`remember` accept only `include`/`visibility` narrowing; a model-supplied scope argument is ignored and tested.
- [ ] `tools/list` omits `promote` when the grant lacks it.
- [ ] Test vectors for the HMAC chain are committed and a reviewer sign-off is recorded in the issue.

**Blockers.** Issue 1; CON-18 (local daemon and MCP server); connectors note (MCP auth and `cacheScope` in §5); design §9 (signed scoped context tokens).

### 7. Promotion privacy gate: PII checks, System One judgments, de-identification and approval queue

**What to build.** The ordered gate from section 7.3: hard denies, scrub and PII detection, `DecisionController` questions `is_generally_useful` and `contains_personal_data`, a System Two de-identification rewrite re-checked after rewriting, an optional `k`-customer support threshold, and an `approval` queue (`oort proposals list|approve|reject`). A consolidation job proposes promotions from corroborating agents. System One may only deny or route to approval.

**Acceptance criteria**
- [ ] No code path lets a System One "yes" override a hard deny (test with a stubbed controller returning 1.0).
- [ ] A de-identified rewrite containing a name, email or id from the source is rejected by the post-rewrite check.
- [ ] With `k=10` and fewer supporting customers, user-derived generalisations stay pending.
- [ ] Proposals survive a daemon restart and every decision is audited with approver identity.
- [ ] Eval: on a seeded set with planted PII, zero planted PII strings reach the hive (report the number tested).

**Blockers.** Issue 5. Design §6.2 Stage 0 (scrubber, A7), §6.3 (`DecisionController`), §13 (Observatory for the later UI).

### 8. Hive conflict reconciliation across agents (SUPERSEDE, CORRECT, trust gate)

**What to build.** Extend reconciliation to hive candidates: order by observation time, close the later-observed memory when an older observation arrives late, keep superseded contributions as history, support CORRECT vs SUPERSEDE, add a per-agent `trust` on the grant and a `needs-review` state with the `contested` label, and serialise hive writes per node (guarded writes or a queue). Enforce "no cross-level supersede": a narrower observation may only REINFORCE (anonymous counter) or ADD an override.

**Acceptance criteria**
- [ ] Two agents asserting contradictory facts produce one current hive memory, one superseded memory with both contributor lists, and correct `validFrom/validTo/expiredAt` by observation time.
- [ ] A late-arriving older claim does not supersede a newer one.
- [ ] A contradiction from a low-trust agent becomes `needs-review`, and both claims are served labelled `contested`.
- [ ] An `agent-user` observation contradicting a hive fact leaves the hive row byte-identical (test).
- [ ] 50-agent concurrency test shows no lost updates and no duplicate currents.

**Blockers.** Issue 5. Temporal research note (REFINE/SUPERSEDE/CORRECT, out-of-order guard); design §5.4, §6.2 Stage C.

### 9. Forget cascade: `forgetCustomer` through derived hive memories, with receipts

**What to build.** `forgetCustomer(U)`: tombstone U's nodes, follow `derivedFrom` via a keyed `customerRef` index to hive memories, delete sole-contributor rows, mark shared ones `needs-rederive` and regenerate or delete under the support threshold, cancel pending proposals, delete the `customerRef` mapping, and return a receipt of counts per node. Idempotent and re-runnable; promote-vs-forget races resolved by tombstones in the guarded write. The crypto-shred of the customer DEK is a Phase 3 hook, stubbed locally as physical delete.

**Acceptance criteria**
- [ ] After `forgetCustomer(U)`, no node reachable by any grant returns anything derived from U (checked with canaries planted in U's memories and in hive memories derived from them).
- [ ] A hive memory supported by U and another customer survives without U's contribution; with support below `k` it is removed.
- [ ] A promote racing a forget never leaves a derived hive row (property test with interleavings).
- [ ] Re-running the cascade is a no-op; the receipt matches the audit log.
- [ ] Audit entries remain but cannot be linked to U after the cascade.

**Blockers.** Issues 5 and 7. Design §14.3 (right to erasure, receipts, purge schedule).

### 10. Cloud: per-level DEKs, grant-checked key unwrap and cache-key rules

**What to build.** The DEK hierarchy in section 8.3 (customer DEK for user-bearing nodes, agent DEK, hive DEKs, per-node blind-index keys), a key-service `unwrap(keyId, grant)` that re-checks the node, zero-knowledge key distribution through token-carried wrapped key grants with attenuation, and a single cache-key helper `H(grant.digest ‖ query ‖ policyVersion ‖ nodeVersion)` used by every cache in the cloud path. Apply the isolation suite from issue 2 to the Convex and Atlas adapters, and add the production canary probe.

**Acceptance criteria**
- [ ] A store-layer bug test (adapter deliberately skipping its filter) returns ciphertext only, because unwrap refuses a grant outside the key's node.
- [ ] Destroying a customer DEK makes that customer's nodes unreadable while hive memories derived from them are handled only by the cascade (issue 9), not by the key.
- [ ] Attenuating a token removes its wrapped key grants; a zero-knowledge client cannot decrypt a node it was attenuated away from.
- [ ] No cache in the cloud path is keyed without `grant.digest` (lint or import guard plus test); `tools/list` uses private cache scope.
- [ ] The production canary probe is deployed and alerts in a staged leak drill.

**Blockers.** Phase 3 cloud foundations (Convex control plane, Atlas warm tier, KMS; design §9 and §10). Issues 1, 2, 6 and 9. Design §14 (deletion and audit).
